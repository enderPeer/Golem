# Neural Golem: memory, dialogue and controlled evolution

The neural backend is a real recurrent network trained from random initialization. It is separate from the legacy sparse-table worlds, which retain their original reproduction semantics and replay paths.

## Model

The default network uses 256 UTF-8 byte values and four role/control tokens, 128-dimensional embeddings, two GRU layers with 256 hidden units, and a 260-way output. It has **791,300 parameters**. Recurrent state passes through the full input and then through each generated byte. The synthetic-memory model is smaller: 32-dimensional embeddings, one 64-unit GRU and **44,036 parameters**.

Text documents provide contiguous next-byte training. Dialogue uses explicit USER, ASSISTANT and END markers and scores assistant outputs only. Padding never contributes to the loss. User prompts and prior turns condition inference; responses are not supplied by a hosted/pretrained model.

## Runtime

```bash
python3 -m venv .venv-neural
.venv-neural/bin/python -m pip install -r requirements-neural.txt
./golem neural prepare --output data/neural-dialogue
```

The `golem` launcher uses `.venv-neural` for neural commands if present. Legacy commands use the original interpreter. No system-wide Python packages, services or drivers need to change for the CPU reference.

An optional separate `.venv-rocm` uses the pinned AMD user-space packages in `requirements-rocm.txt`. A compatible kernel driver and permissions are still required. `HIP_VISIBLE_DEVICES=1 .venv-rocm/bin/python ops/probe_rocm.py` is specific to the verified deployment's device ordering: the probe refuses to allocate unless the exposed device is an RX 9070 XT. It caps its allocator at approximately 4 GiB. A successful probe establishes only basic forward/backward compatibility.

## A measurable memory gate

```bash
bash ops/run_neural.sh memory
./golem neural status --run-dir runs/neural-memory
```

The model learns a random digit followed by 32 or 64 unrelated non-digit distractor bytes, then predicts the digit. Only the answer is scored. Independent held-out distractors measure generalization; replacing the original digit with a space tests whether the model used the source cue. Balanced digits give a 10% chance baseline. The success criterion is at least 95% accuracy at both distances with a substantial drop after cue removal. This does not demonstrate conversational understanding.

## Four candidates versus ordinary training

```bash
bash ops/run_neural.sh benchmark
bash ops/run_neural.sh compare
./golem neural status --run-dir runs/neural-compare
./golem neural chat --checkpoint runs/neural-compare/ordinary_champion.pt
./golem neural chat --checkpoint runs/neural-compare/evolution_champion.pt
```

The pilot compares one ordinarily trained network with a population of four fixed-shape networks. Gradient descent updates weights. Between rounds, population-based training copies the strongest candidate's model and AdamW state into the weakest and changes learning rate/dropout. Tensor checkpoint inheritance replaces byte-by-byte VM copying in this explicitly separate experiment.

Both arms receive the same total optimizer updates, shapes, global batch schedule, processed bytes, supervised targets and validation forward-batch budget. **This is operation matching, not a claim that elapsed CPU time is identical.** Initialization, model copying, evaluation and checkpoint overhead are included in separately reported CPU/wall measurements. PBT has four founder seeds; a further best-of-four independent-training control and multiple experiment seeds are needed before broad claims.

Test data is used only after both arms have finished, on validation-selected checkpoints. The first pilot is allowed to show that ordinary training performs better. A single favorable run would not establish a general advantage for evolution.

The default comparison has four rounds, so actual inheritance occurs. A four-update pipeline benchmark has only one round and does not establish evolutionary benefit.

`bash ops/run_neural.sh language` runs a longer 4,800-update-per-arm comparison in `runs/neural-language`, with twelve population rounds and a 20-minute training-session cap. Current validation-selected champions are published at checkpoints, so terminal inference can use a coherent saved snapshot while training continues. Reaching the time limit before both arms finish means the comparison is incomplete; resume it explicitly rather than treating unequal work as a result.

## Resource policy

Neural launchers use an isolated user service, two-core CPU quota, two Torch threads, 8 GiB RAM, low CPU/I/O priority and the same 20 GiB project disk monitor. The existing one-hour English job can continue separately. GPU compatibility probes are separate from the CPU-matched experiment and never silently change its execution backend.

## Low-bit scope

`./golem ternary-check` verifies two-bit packing, signed-int8 inputs and int32 accumulation against exact integer arithmetic. Neural model utilities also provide a **post-training ternary clone** for accuracy experiments. This clone still executes floating-point operations. It is not native BitNet training, a packed inference kernel, or an FPGA/PIM accelerator. See [research boundaries](research-boundaries.md) for the evidence needed to make hardware or open-ended-evolution claims.

`./golem neural quantize --checkpoint runs/neural-compare/ordinary_champion.pt --output runs/neural-ternary` writes genuinely packed matrix payloads plus residual floating-point tensors and quantization scales. It verifies exact recovery of the quantized matrices and compares validation loss. The separately saved `ternary-reference.pt` runs through floating-point PyTorch; packed execution is not implemented.

`./golem neural relevance --checkpoint runs/neural-compare/ordinary_champion.pt` compares held-out answer likelihood with its actual user prompt and a shuffled user prompt. This is a descriptive prompt-sensitivity test, not a human relevance or factual-correctness score.

`bash ops/run_neural.sh qat` performs a separate bounded adaptation of the ordinary checkpoint. It keeps floating-point master weights, uses ternary GRU/output matrix values during forward passes, and uses a straight-through gradient estimator. The embedding and biases remain floating point. This is additional quantization-aware fine-tuning, not native BitNet pretraining or an equal-compute comparison against the original checkpoint. Test data is excluded from the QAT training/selection procedure.

The selected `runs/neural-qat/qat-reference.pt` already contains ternary matrices with their learned scales. Export it using `./golem neural quantize --checkpoint runs/neural-qat/qat-reference.pt --output runs/neural-qat-packed --already-ternary` to preserve those scales exactly.
